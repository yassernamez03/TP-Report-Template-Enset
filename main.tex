\section{Introduction}

Ce devoir consiste \`a d\'evelopper une application web de d\'eclaration et de suivi d'incidents informatiques et de cybers\'ecurit\'e (malware, phishing, panne r\'eseau, fuite de donn\'ees, etc.). L'application g\`ere trois types d'utilisateurs : \texttt{EMPLOYEE}, \texttt{TECHNICIAN} et \texttt{ADMIN}.

\begin{objectifbox}
\begin{itemize}
  \item Mettre en place l'authentification avec JWT.
  \item G\'erer les r\^oles et prot\'eger les routes du backend et de React.
  \item Contr\^oler l'acc\`es aux donn\'ees (propri\'etaire d'un incident).
  \item Valider les donn\'ees et g\'erer proprement les erreurs.
  \item Fournir un tableau de bord et un historique des incidents.
\end{itemize}
\end{objectifbox}

\subsection{Technologies utilis\'ees}

\begin{itemize}
  \item \textbf{Backend} : Spring Boot 3, Spring Security, Spring Data JPA, Bean Validation, jjwt, base H2.
  \item \textbf{Frontend} : React (Vite), React Router, Axios.
  \item \textbf{Tests} : Postman.
\end{itemize}

\subsection{Travail de recherche : relations JPA}

\begin{definitionbox}{\texttt{@ManyToOne} et \texttt{@OneToMany}}
\texttt{@ManyToOne} indique que plusieurs objets d'une classe sont li\'es \`a un seul objet d'une autre classe. Dans la base, la cl\'e \'etrang\`ere est plac\'ee dans la table qui porte l'annotation. \texttt{@OneToMany} est le c\^ot\'e inverse : un objet poss\`ede une liste d'objets, avec \texttt{mappedBy} pour indiquer le champ \texttt{@ManyToOne} correspondant.
\end{definitionbox}

Dans notre projet, plusieurs incidents sont li\'es \`a un utilisateur :

\begin{lstlisting}[language=Java]
@ManyToOne(fetch = FetchType.LAZY)
private User createdBy;

@ManyToOne(fetch = FetchType.LAZY)
private User assignedTo;
\end{lstlisting}

\textbf{LAZY ou EAGER ?}

\begin{center}
\begin{tabular}{p{2cm}p{6.5cm}p{5.5cm}}
\toprule
 & \textbf{Fonctionnement} & \textbf{Inconv\'enient} \\
\midrule
\textbf{EAGER} & L'objet li\'e est charg\'e imm\'ediatement, avec l'entit\'e principale. & Charge des donn\'ees inutiles et ajoute des jointures. \\
\textbf{LAZY} & L'objet li\'e n'est charg\'e que lors du premier acc\`es. & Provoque une \texttt{LazyInitializationException} hors transaction. \\
\bottomrule
\end{tabular}
\end{center}

\textbf{Justification de nos choix :}
\begin{itemize}
  \item Nous utilisons \texttt{LAZY} partout : l'utilisateur li\'e \`a un incident n'est charg\'e que si on en a besoin. Par d\'efaut, \texttt{@ManyToOne} est EAGER, d'o\`u le choix explicite de LAZY.
  \item Le probl\`eme du LAZY est r\'esolu en convertissant les entit\'es en DTO \`a l'int\'erieur d'un service annot\'e \texttt{@Transactional}. Les entit\'es ne sont jamais renvoy\'ees directement en JSON.
  \item Nous n'avons pas utilis\'e de \texttt{@OneToMany} (pas de liste d'incidents dans \texttt{User}) : ce n'est pas n\'ecessaire, et cela \'evite les boucles de s\'erialisation JSON. L'historique et les notes sont r\'ecup\'er\'es avec des requ\^etes de repository.
\end{itemize}

Lors de l'inscription, le r\^ole est impos\'e par le backend (\texttt{Role.EMPLOYEE}). L'objet \texttt{RegisterRequest} ne contient pas de champ \texttt{role} : l'utilisateur ne peut donc pas choisir son r\^ole. Les mots de passe sont encod\'es avec \textbf{BCrypt}.

\subsection{Travail de recherche : les claims JWT}

\begin{definitionbox}{Qu'est-ce qu'un claim ?}
Un JWT est compos\'e de trois parties : \emph{header}, \emph{payload} et \emph{signature}. Le payload contient des \textbf{claims}, c'est-\`a-dire des informations sur l'utilisateur et sur le token. Il existe des claims standards (\texttt{sub} : sujet, \texttt{iat} : date de cr\'eation, \texttt{exp} : date d'expiration) et des claims personnalis\'es, comme le r\^ole.
\end{definitionbox}

Notre token contient : l'email (\texttt{sub}), le r\^ole (claim \texttt{role}), la date de cr\'eation (\texttt{iat}) et la date d'expiration (\texttt{exp}).

\textbf{Ajouter un r\^ole dans le token :}

\begin{lstlisting}[language=Java]
Jwts.builder()
    .subject(email)
    .claim("role", role)
    .issuedAt(now)
    .expiration(new Date(now.getTime() + expirationMs))
    .signWith(key)
    .compact();
\end{lstlisting}

\textbf{R\'ecup\'erer un claim :}

\begin{lstlisting}[language=Java]
Claims claims = Jwts.parser().verifyWith(key).build()
        .parseSignedClaims(token).getPayload();
String email = claims.getSubject();
String role  = claims.get("role", String.class);
\end{lstlisting}

\textbf{V\'erifier l'expiration :} la m\'ethode \texttt{parseSignedClaims} v\'erifie automatiquement la signature et la date d'expiration. Si le token est expir\'e, elle l\`eve une \texttt{ExpiredJwtException} (sous-classe de \texttt{JwtException}). Si le token est invalide, une autre \texttt{JwtException} est lev\'ee. Dans les deux cas, le filtre n'authentifie pas la requ\^ete et l'API r\'epond \textbf{401}.

La dur\'ee de vie du token est de \textbf{5 minutes} (propri\'et\'e \texttt{jwt.expiration-minutes}), ce qui permet de tester facilement l'expiration.

\section{Configuration de Spring Security}

\begin{itemize}
  \item Routes publiques : \texttt{/auth/**} et \texttt{/h2-console/**}.
  \item Routes prot\'eg\'ees : \texttt{/api/**} (token obligatoire).
  \item \texttt{/api/admin/**} : r\'eserv\'e au r\^ole ADMIN.
  \item Sessions : \texttt{SessionCreationPolicy.STATELESS} (aucune session c\^ot\'e serveur).
  \item CORS : autorise l'origine \texttt{http://localhost:5173}.
\end{itemize}

\begin{lstlisting}[language=Java]
http
  .csrf(csrf -> csrf.disable())
  .cors(Customizer.withDefaults())
  .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
  .authorizeHttpRequests(auth -> auth
      .requestMatchers("/auth/**").permitAll()
      .requestMatchers(new AntPathRequestMatcher("/h2-console/**")).permitAll()
      .requestMatchers("/api/admin/**").hasRole("ADMIN")
      .requestMatchers("/api/**").authenticated()
      .anyRequest().authenticated())
  .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class);
\end{lstlisting}

\subsection{Le filtre JWT}

Le filtre \texttt{JwtFilter} s'ex\'ecute \`a chaque requ\^ete :
\begin{enumerate}
  \item il lit le header \texttt{Authorization: Bearer ...} ;
  \item il v\'erifie le token et extrait l'email et le r\^ole ;
  \item il v\'erifie que le compte existe et qu'il est activ\'e (\texttt{enabled}) ;
  \item il place l'utilisateur et son r\^ole dans le \texttt{SecurityContextHolder}.
\end{enumerate}

Si le token est absent, invalide ou expir\'e, aucune authentification n'est cr\'e\'ee et Spring Security renvoie une r\'eponse \textbf{401} en JSON.

\subsection{Travail de recherche : s\'ecurisation par r\^ole}

\begin{itemize}
  \item \texttt{hasRole('ADMIN')} v\'erifie que l'utilisateur poss\`ede l'autorit\'e \texttt{ROLE\_ADMIN} (le pr\'efixe \texttt{ROLE\_} est ajout\'e automatiquement).
  \item \texttt{hasAuthority('ROLE\_ADMIN')} compare la cha\^ine exacte, sans ajouter de pr\'efixe.
  \item \texttt{@PreAuthorize} applique une r\`egle d'acc\`es sur une m\'ethode, avant son ex\'ecution.
  \item \texttt{@EnableMethodSecurity} active la prise en compte de \texttt{@PreAuthorize}.
\end{itemize}

Dans le projet, le r\^ole est d\'eclar\'e dans le token, puis transform\'e en autorit\'e \texttt{ROLE\_xxx} par le filtre. Les controllers utilisent ensuite \texttt{@PreAuthorize} :

\begin{lstlisting}[language=Java]
@PostMapping
@PreAuthorize("hasRole('EMPLOYEE')")
public IncidentResponse create(@Valid @RequestBody CreateIncidentRequest request) { ... }

@PutMapping("/{id}/assign/{technicianId}")
@PreAuthorize("hasRole('ADMIN')")
public IncidentResponse assign(@PathVariable Long id, @PathVariable Long technicianId) { ... }
\end{lstlisting}

\section{Contr\^ole du propri\'etaire d'un incident}

Un employ\'e peut tester directement l'URL \texttt{GET /api/incidents/12} dans Postman, m\^eme si l'incident ne lui appartient pas. Masquer un bouton dans React ne suffit donc pas : le backend doit v\'erifier l'acc\`es.

\textbf{Solution :} la classe \texttt{CurrentUser} r\'ecup\`ere l'utilisateur connect\'e gr\^ace \`a \texttt{SecurityContextHolder} :

\begin{lstlisting}[language=Java]
String email = SecurityContextHolder.getContext()
        .getAuthentication().getName();
User user = userRepository.findByEmail(email).orElseThrow(...);
\end{lstlisting}

Ensuite, la m\'ethode \texttt{checkAccess} du service compare cet utilisateur au propri\'etaire de l'incident :

\begin{lstlisting}[language=Java]
private void checkAccess(Incident incident, User user) {
    boolean allowed = switch (user.getRole()) {
        case ADMIN -> true;
        case EMPLOYEE -> incident.getCreatedBy().getId().equals(user.getId());
        case TECHNICIAN -> incident.getAssignedTo() != null
                && incident.getAssignedTo().getId().equals(user.getId());
    };
    if (!allowed) {
        throw new ApiException(HttpStatus.FORBIDDEN, "Acces interdit");
    }
}
\end{lstlisting}

Cette m\'ethode est appel\'ee pour consulter un incident, changer son statut et ajouter une note. Un employ\'e qui demande l'incident d'un autre re\c{c}oit donc une r\'eponse \textbf{403}.

\textbf{Annotation} & \textbf{R\^ole} \\

\section{Gestion des exceptions}

Les erreurs sont centralis\'ees dans une classe \texttt{GlobalExceptionHandler} annot\'ee \texttt{@RestControllerAdvice} (version de \texttt{@ControllerAdvice} qui renvoie directement du JSON). Chaque m\'ethode annot\'ee \texttt{@ExceptionHandler} g\`ere un type d'erreur.

Une seule exception m\'etier, \texttt{ApiException}, contient le statut HTTP et le message. Toutes les erreurs ont le m\^eme format :

\begin{lstlisting}
{ "status": 404, "message": "Incident introuvable" }
\end{lstlisting}

\begin{center}
\begin{tabular}{p{5.5cm}ll}
\toprule
\textbf{Cas g\'er\'e} & \textbf{Code} & \textbf{Message} \\
\midrule
Utilisateur introuvable & 404 & Utilisateur introuvable \\
Incident introuvable & 404 & Incident introuvable \\
Email d\'ej\`a utilis\'e & 409 & Email d\'ej\`a utilis\'e \\
Mauvais mot de passe (connexion) & 401 & Email ou mot de passe incorrect \\
Compte d\'esactiv\'e & 403 & Compte d\'esactiv\'e \\
Acc\`es interdit & 403 & Acc\`es interdit \\
Donn\'ees invalides & 400 & Message de la validation \\
\bottomrule
\end{tabular}
\end{center}

\begin{center}
\begin{tabular}{lp{5cm}p{6cm}}
\toprule

\midrule

\subsection{Gestion du JWT}

Apr\`es la connexion, le token, le r\^ole et le nom sont stock\'es dans le \texttt{localStorage}. Un \textbf{interceptor Axios} ajoute automatiquement le header \texttt{Authorization} \`a chaque requ\^ete :

\begin{lstlisting}[language=Java]
api.interceptors.request.use((config) => {
  const token = localStorage.getItem("token");
  if (token) {
    config.headers.Authorization = "Bearer " + token;
  }
  return config;
});
\end{lstlisting}

\subsection{Expiration du JWT}

Un second interceptor traite les r\'eponses. Quand le backend renvoie \textbf{401}, le token est supprim\'e et l'utilisateur est redirig\'e vers la page Login avec le message \og Votre session a expir\'e \fg. Les erreurs 401 de \texttt{/auth/*} (mauvais mot de passe) sont ignor\'ees pour ne pas afficher ce message \`a tort.

\begin{lstlisting}[language=Java]
api.interceptors.response.use(
  (response) => response,
  (error) => {
    const isAuthRequest = error.config?.url?.startsWith("/auth/");
    if (error.response?.status === 401 && !isAuthRequest) {
      localStorage.clear();
      window.location.href = "/login?expired=1";
    }
    return Promise.reject(error);
  }
);
\end{lstlisting}

\subsection{Protection des routes}

\begin{itemize}
  \item \texttt{ProtectedRoute} : si l'utilisateur n'a pas de token, il est redirig\'e vers \texttt{/login}.
  \item \texttt{RoleRoute} : si le r\^ole n'est pas dans la liste autoris\'ee, l'utilisateur est redirig\'e vers l'accueil. Exemple : \texttt{/admin/users} n'est accessible qu'\`a un ADMIN.
\end{itemize}

\begin{alertbox}
La protection des routes React am\'eliore l'exp\'erience utilisateur, mais la v\'eritable s\'ecurit\'e est assur\'ee par le backend.
\end{alertbox}

 & \textbf{Access Token} & \textbf{Refresh Token} \\
\midrule
\textbf{R\^ole} & Envoy\'e \`a chaque requ\^ete pour acc\'eder \`a l'API. & Sert uniquement \`a obtenir un nouvel Access Token. \\
\textbf{Dur\'ee de vie} & Courte (quelques minutes). & Longue (jours ou semaines). \\
\textbf{Risque} & Limit\'e, car il expire vite. & Plus \'elev\'e, il doit \^etre mieux prot\'eg\'e. \\
\bottomrule
\end{tabular}
\end{center}

\textbf{Fonctionnement :} \`a la connexion, le serveur renvoie les deux tokens. Quand l'Access Token expire, le client envoie le Refresh Token \`a \texttt{POST /auth/refresh} et re\c{c}oit un nouvel Access Token, sans que l'utilisateur ressaisisse son mot de passe.

\textbf{D\'econnexion :} le client supprime les deux tokens, et le serveur doit invalider (supprimer ou marquer comme r\'evoqu\'e) le Refresh Token enregistr\'e, pour qu'il ne puisse plus servir.
